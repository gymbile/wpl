# WPL 1.9.0 — Recommended Goal-Category & Dietary-Tag Vocabularies (Design / Scope)

**Date:** 2026-07-07
**Target release:** WPL **v1.9.0** (minor, additive, **non-breaking**)
**Status:** Scoping — awaiting review

## Problem

Downstream consumers (gymbile) maintain their own goal-category and dietary
vocabularies because WPL doesn't define them:

- `Goal.category` is a **free-form string** in the schema (`{"type": "string"}`),
  and **no published validator enforces any goal vocabulary**. The
  `weight_loss / muscle_gain / …` list lives only in gymbile's in-house code.
- **Dietary tags** (`vegetarian / vegan / gluten_free / dairy_free`) are **absent
  from WPL entirely** — gymbile defines and duplicates them locally.

This forces every consumer to invent (and drift on) the same vocabularies. WPL
should offer a **recommended, machine-readable** vocabulary for both, so
consumers share one source — without breaking the language's current tolerance
for free-form strings.

## Goals

1. Introduce a **recommended goal-category vocabulary** (including
   `general_fitness`) — documented + machine-readable, **soft-validated**.
2. Introduce a **dietary-tag vocabulary** and an optional carrier field on
   nutrition activities — **soft-validated**.
3. Keep everything **additive and non-breaking** → minor bump to **v1.9.0**.
4. Let gymbile delete its local copies and read these from the published libs
   (closing the SSOT loop started by the in-repo unification).

## Non-goals (explicitly out of scope)

- **Equipment.** WPL already has a requirement-side `Equipment` `$def`
  (`{id, name, required, alternatives[]}`). Gymbile's `equipment` is a coarse
  *client-access* bucket (`full_gym`/`bodyweight`/…) — an **input** concept we
  deliberately keep out of the plan standard. Equipment stays Intake-owned.
- **Typed/closed enums.** Constraining `Goal.category` to a fixed enum would
  reject existing plans that use off-list categories → breaking (v2.0.0). We keep
  `type: string` and validate softly.
- **WPL-AI compiler grammar changes** beyond accepting the new optional field.

## Design

### 1. Recommended goal-category vocabulary

- **Schema:** `Goal.category` stays `{"type": "string"}` (non-breaking). Add a
  `description` cross-referencing the recommended list, and (optional) an
  `examples` array. Do **not** add an `enum`.
- **Machine-readable list:** new `data/goal-categories.json` in the `wpl` repo —
  an array of `{ id, label, description }`, the canonical recommended set:
  `weight_loss, muscle_gain, endurance, flexibility, strength, mental_wellness,
  nutrition, habit, general_fitness, custom`. (`general_fitness` is the addition;
  `custom` remains the documented escape hatch for off-list intent.)
- **Validation (soft):** validators load the list and emit a **warning**
  (not an error) when `Goal.category` is outside it and isn't `custom`. Free
  strings remain valid.

### 2. Dietary-tag vocabulary + carrier

- **Schema:** add optional `dietary_tags` to `NutritionActivity`
  (`schema/v1.schema.json` ~line 789): `{"type": "array", "items": {"type":
  "string"}}`. Optional → additive, non-breaking. (Chosen over
  `NutritionPrescription` so tags describe the meal/day, not a single macro
  prescription.)
- **Machine-readable list:** new `data/dietary-tags.json` — canonical recommended
  set: `vegetarian, vegan, gluten_free, dairy_free` (room to grow: `pescatarian,
  keto, halal, kosher, nut_free, low_fodmap` — include the initial four now; the
  file is the extension point).
- **Validation (soft):** validators warn on `dietary_tags` entries outside the
  list. Free strings remain valid.

### 3. Conformance

- `conformance/valid/`: a plan using `category: "general_fitness"` and a
  nutrition activity with `dietary_tags: ["vegan"]`.
- If the conformance suite models warnings: a fixture asserting an unknown
  category/tag **warns but validates**.
- Update an existing nutrition example to show `dietary_tags`.

## Cross-repo change list & release order

Additive minor version **v1.9.0**. Release strictly in dependency order:

1. **`wpl` (canonical)** — `schema/v1.schema.json` (add `dietary_tags`; goal
   `category` description/examples), `data/goal-categories.json`,
   `data/dietary-tags.json`, `spec/SPECIFICATION.md` (document both vocabularies +
   soft-validation semantics), `conformance/` fixtures, `CHANGELOG.md`
   (`## [1.9.0]`). **Tag `v1.9.0`.**
2. **`wpl-validator-ts` (npm `wpl-validator`)** — load the two lists; soft-warn on
   off-list values; tests; bump to `1.9.0`; publish (OIDC).
3. **`wpl-validator-ex` (Hex `wpl_validator`)** — parity: soft-warn; tests; bump;
   publish.
4. **`wpl-ai`** — **assess only.** If the DSL surfaces goal category (GOALS block)
   or meal dietary info, accept the new optional field + recommended vocab; else
   no change. Bump/publish only if touched.
5. **`wpl.dev`** — docs pages for both vocabularies; bump the referenced spec
   version to 1.9.0.
6. **`gymbile_backend`** — upgrade `wpl_validator`/`wpl_ai` deps to 1.9.0;
   re-vendor any vendored data; **delete the gymbile-local goal-category list and
   read `general_fitness` et al. from the published lib**; point
   `Intake.diet_vocab/0` at the published dietary-tag list. Keep the drift-guard
   tests (now guarding against the *published* source). This closes the SSOT loop.

## Backward compatibility

Every change is additive: `Goal.category` stays a free string; `dietary_tags` is
optional; validation is warn-only. **All existing v1.x plans validate unchanged.**
Hence a minor bump (v1.9.0), not major.

## Testing

- `wpl`: JSON-schema validates the new fixtures; conformance runner passes.
- Validators (ts + ex): unit tests for known-value (no warning), off-list value
  (warning, still valid), and absence (no warning). Parity between the two libs.
- `gymbile_backend`: after upgrade, existing intake/vocab drift-guard tests point
  at the published lists; full suite green.

## Open questions to settle during implementation

- Exact home for the machine-readable lists (`data/*.json` vs extending
  `entities.json`) — follow whatever pattern the exercise catalog uses.
- Whether the conformance suite has a first-class "warning" assertion channel, or
  warnings are validator-only (affects fixture #3).
- Whether `wpl-ai` surfaces goal category / dietary tags at all (drives step 4).
